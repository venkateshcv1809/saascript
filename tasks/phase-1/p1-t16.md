# chore: Setup Unit and Integration Testing for Initial Services

**1. Rationale:**
While individual services have established basic unit testing frameworks (P1-T13, P1-T14, P1-T15), this task significantly enhances our testing strategy by focusing on advanced unit testing patterns and, crucially, establishing a clear framework for **backend integration testing** across multiple microservices. Implementing common mocking strategies, reusable test utilities, and defining how tests span microservice boundaries is vital for verifying complex interactions (e.g., API Gateway routing to Auth Service), catching integration-level regressions, and ensuring the robust behavior of the entire SaaScript system. This aligns directly with our project's core intention to learn and experience best practices, building a comprehensive testing pyramid that also lays the groundwork for future End-to-End (E2E) testing (P1-T17).

**2. Goal:**
To implement advanced unit testing patterns (e.g., standardized dependency mocking, reusable test utility functions) and establish the foundational framework for running **backend-to-backend integration tests** that verify interactions between multiple services (specifically focusing on API Gateway and Auth Service communications). This includes refining existing Jest configurations, creating shared test helper files, defining how these tests execute within the `e2e/` directory, and documenting the strategy for running and managing these crucial cross-service test suites, all **without involving browser automation or UI interaction**.

**3. Detailed Steps:**
* Step 1: **Review and Enhance Service-Specific Jest Configurations.**
    Navigate to `modules/gateway/jest.config.js`, `modules/auth_service/jest.config.js`, and `frontend/web/jest.config.js`. Review these files to ensure they incorporate best practices for:
    * **Module Path Aliases:** Confirm `moduleNameMapper` entries are correctly configured to resolve `tsconfig.json` path aliases, promoting cleaner imports in tests.
    * **`setupFilesAfterEnv`:** Ensure setup files for Jest matchers (e.g., `@testing-library/jest-dom` for frontend, or custom matchers for backend) are correctly referenced.
    * **Consistent Coverage Reporting:** Verify `collectCoverageFrom` and `coverageDirectory` settings are aligned for unified reporting later.
* Step 2: **Define Common Mocking and Test Utility Patterns (Unit Testing).**
    Document and outline strategies for advanced unit testing patterns, specifically focusing on how to effectively mock external dependencies (e.g., database repositories, external API calls, other microservices' clients) using Jest's mocking capabilities. Guide on creating a dedicated shared library (e.g., in `scripts/test/utils/` or `modules/libs/test-utils/`) for reusable test helper functions, mock factories, and common test data generators that can be imported and utilized across different service unit test suites.
* Step 3: **Establish Backend Integration Testing Strategy and Structure.**
    Outline the architectural approach for integration tests that specifically verify the communication and data flow between the API Gateway and the Auth Service, as well as their interactions with shared infrastructure. This strategy will emphasize a **non-UI based, programmatic approach**.
    * **Test Environment Setup:** Define the process to ensure all necessary backend services (API Gateway, Auth Service) and core infrastructure components (PostgreSQL, Redis, RabbitMQ, Kafka, etc., from P1-T1) are running via Docker Compose before integration tests execute. This typically involves using the `yarn start:dev:infra` script.
    * **Test Runner Location:** Backend integration tests that span multiple services will reside in the **`e2e/` directory** at the monorepo root. This directory will also house future UI-driven E2E tests (P1-T17), so a clear naming convention (e.g., `*.integration.spec.ts` vs `*.e2e-spec.ts`) and/or a dedicated subfolder (e.g., `e2e/backend-integration/`) might be considered for segregation.
    * **Test Setup/Teardown:** Plan how to prepare and clean up test-specific data for integration tests. This could involve using dedicated test databases, transactional rollbacks for data changes, or programmatic data seeding/cleansing via direct database client calls or service APIs.
    * **HTTP Interactions:** Reiterate the use of `supertest` for making direct HTTP requests to the API Gateway as the entry point for these integration tests, and potentially direct service-to-service calls if the test scope requires it.
* Step 4: **Create Basic Backend Integration Test Skeleton.**
    Within the `e2e/` directory (or its designated subfolder for backend integration tests), create a placeholder file (e.g., `e2e/backend-integration/auth-gateway-flow.spec.ts`). This file will establish the basic structure for an integration test that conceptually involves sending a request to the API Gateway and verifying a response that would demonstrate successful interaction with the Auth Service and potentially a database. **This test must explicitly avoid any browser automation or UI rendering.**
* Step 5: **Update Root `package.json` for Integration Tests.**
    Review the monorepo root `package.json` (from P1-T2) to ensure the `test:all` script can eventually discover and execute these new integration tests. Consider adding a dedicated `test:backend-integration` script at the root (`saascript/package.json`) that specifically targets these tests in the `e2e/` directory, potentially using a dedicated Jest config (e.g., `jest.config.backend-integration.js`) for the `e2e/` folder to manage specific setup/teardown for this test type.
* Step 6: **Document Advanced Testing Practices and Test Pyramid.**
    Update `docs/development-workflow.md` (specifically the "Comprehensive Testing" section) and `docs/code-style-guidelines.md` to:
    * Detail the common mocking strategies and test utility patterns for unit tests.
    * Clearly describe the **backend integration testing strategy**, including environment setup, test location, and data management.
    * Explicitly explain the role of unit, **backend integration**, and future **UI-driven End-to-End (E2E)** tests in the overall **testing pyramid**. Clearly distinguish backend integration tests (which verify interactions *between* services via their APIs, without a UI) from UI-driven E2E tests (which simulate user interaction through the frontend).
