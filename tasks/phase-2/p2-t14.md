# chore(saascript-frontend-web): Implement Client-Side Authorization with CASL

**1. Rationale:**
While authentication verifies "who a user is," authorization determines "what a user can do." Implementing a client-side authorization framework like CASL from early development is a crucial best practice for two main reasons:
* **Preventing Rework:** By making UI components and navigation permission-aware from the start, we avoid costly refactoring when roles and permissions become more complex.
* **Enhanced User Experience & Security:** It allows for dynamic rendering of UI elements (e.g., hiding/showing buttons, menu items) based on the user's capabilities, providing a tailored and secure experience. It also provides an initial layer of access control at the UI level, complementing server-side authorization checks.
This task ensures that the `saascript-frontend-web` is built with authorization in mind, laying foundational groundwork for a robust security posture and efficient feature development.

**2. Goal:**
To successfully integrate the CASL.js library into the `saascript-frontend-web` application. This includes:
* Installing CASL and its React integration.
* Defining a basic `Ability` (permissions) model based on the authenticated user's role or attributes.
* Implementing conditional rendering for simple UI elements (e.g., a "Manage Users" button) and navigation links based on these abilities.
* Ensuring the user's role or abilities are correctly processed after login (e.g., from the JWT payload).

**3. Detailed Steps:**
* Step 1: **Navigate to the Web Frontend Application Directory.**
    Ensure your current working directory is `frontend/web/`.
* Step 2: **Install CASL Dependencies.**
    Install `casl/ability` and `casl/react` as dependencies within `frontend/web/`.
* Step 3: **Define User Abilities (CASL `Ability`).**
    Create a new file (e.g., `frontend/web/src/lib/ability.ts`) that defines functions or logic to create a CASL `Ability` instance based on a user's role or other authorization attributes. Initially, this can be very basic (e.g., `isAdmin: boolean` from JWT payload).
* Step 4: **Integrate CASL with React Context.**
    Set up a React Context provider (e.g., `AbilityContext.tsx`) that makes the `Ability` instance available throughout the application. This context will be updated when the user's authentication state changes.
* Step 5: **Update Login/Registration Flow to Include Abilities.**
    Modify the login (and potentially registration) success logic in `frontend/web/pages/login.tsx` (and `register.tsx`) to not only store tokens but also to extract or derive the user's roles/abilities from the API response (e.g., from the JWT payload) and update the `Ability` context.
* Step 6: **Implement Conditional UI Rendering.**
    In existing components (e.g., a dashboard header, a navigation menu), use CASL's `Can` component or `useAbility` hook to conditionally render UI elements based on the defined abilities. For example, show an "Admin Panel" link only if the user `can manage 'users'`.
* Step 7: **Install Monorepo Dependencies.**
    Execute the monorepo-wide dependency installation command.
* Step 8: **Build and Run the Web Frontend Application.**
    Build the `saascript-frontend-web` and then start it in development mode.
* Step 9: **Test Client-Side Authorization.**
    Perform manual tests by:
    * Logging in with a user that has specific (e.g., admin) permissions. Verify that corresponding UI elements are visible.
    * Logging in with a user that does not have those permissions. Verify that those UI elements are hidden.
    * (Future: if roles are implemented on backend): Switch roles or user types and observe UI changes.
* Step 10: **Document Client-Side Authorization.**
    Update `docs/frontend.md` and `docs/security.md` to detail the client-side authorization strategy using CASL. Explain how abilities are defined, how they are integrated into the React application, and how UI elements are conditionally rendered. Emphasize that client-side authorization is a UX/security *layer*, not a replacement for server-side authorization.

    ```typescript

    // ...
    <Can I="manage" a="User"> {/* Assuming an ability to 'manage' 'User' for admin */}
      <Link href="/admin-panel">Admin Panel</Link>
    </Can>
    ```
